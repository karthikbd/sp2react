# Releasing to PyPI

## Automated (the only way releases are made)

`.github/workflows/python-publish.yml` runs when a GitHub release is published (or by hand from the
Actions tab). It runs the tests, builds the sdist and wheel reproducibly, checks the wheel declares no
runtime dependencies, writes a CycloneDX SBOM, and publishes with **PyPI Trusted Publishing** (OIDC)
from the GitHub environment `release`, so no API token is stored anywhere. The `release` environment
accepts only `v*` tags, so a run started from a branch cannot publish. It then signs the wheel,
sdist and SBOM with Sigstore and attaches them to the release.

Each release:

```console
$ # bump version in pyproject.toml and src/sp2react/__init__.py; move CHANGELOG [Unreleased] to the
$ # version; add it to docs/whatsnew; add the release's template hashes to scaffold/released_templates.json
$ git switch -c release-{{ version }} && git commit -s -am "Release {{ version }}" && gh pr create --fill
$ # after the pull request's checks pass and it is merged:
$ gh release create v{{ version }} --target main --title v{{ version }} --notes-file CHANGELOG.md
```

The template hashes let `sp2react convert` recognise apps generated by earlier releases, so it can update
their unchanged files and keep the changed ones; a test fails if a published template has no hash.

When the publish run succeeds, `verify-release.yml` downloads the release assets on a fresh runner,
verifies each Sigstore signature against `python-publish.yml`, the tag and the `release` trigger, and
checks that PyPI serves byte-identical files. A red run there means the release must not be trusted.

## Checks before tagging

- The *Security assurance case* ({doc}`security-assurance`) has been re-read against the changes since
  the last release and updated (new inputs, files written, connections, generated-app endpoints); record
  the release in its *Review at release* section.
- `vulnerability-audit.yml` is green and no CodeQL alert of medium severity or higher is open
  ({doc}`dependencies`).
- The `reproducible-build` job is green: two builds of the commit give identical wheel and sdist.
- `pytest -q` passes with statement coverage of 80% or more, and `e2e.yml` passes against MySQL and
  SQL Server.
- `CHANGELOG.md` and `docs/whatsnew/index.md` describe the release; a change to the generated app says
  whether existing apps must be regenerated.
- The wheel's metadata has **no** `Requires-Dist` lines except the extras.
- `python -m sphinx -W -b html docs docs/_build/html` builds with no warnings.

## Hosting this documentation

`.readthedocs.yaml` at the repository root builds these docs on Read the Docs: every push to `main`
updates *latest*, and every tag gets its own versioned docs.

## Verifying a release yourself

1. **Signature and origin:** each asset on the GitHub release has a `.sigstore.json` bundle. Verify it
   was produced by this repository's `python-publish.yml` for that tag, as shown in
   {doc}`/getting_started/install`.
2. **Same bytes as PyPI:** compare the SHA-256 of the files on PyPI with the GitHub assets (the
   `verify-release.yml` workflow does this after every release).
3. **Rebuild it:** check out the tag, then
   `SOURCE_DATE_EPOCH=$(git log -1 --format=%ct) python -m build && python ci/reproducible_sdist.py dist/*.tar.gz`
   with the tools in `ci/requirements-build.txt` on Python 3.11; the results are byte-identical to the release.
