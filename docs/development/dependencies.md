# Dependencies and scanning policy

## How dependencies are chosen, obtained and tracked

- **Runtime:** none. `pyproject.toml` declares `dependencies = []`, the publish workflow fails if the
  wheel declares any, and the `zero-deps` CI job installs and runs the package with nothing else
  installed. The optional extras (`db`, `mysql`, `mssql`) add SQLAlchemy and one database driver,
  imported only inside the functions that use them.
- **The generated app** has its own dependencies (FastAPI, uvicorn, SQLAlchemy; React, Vite) listed in
  `scaffold/templates/backend/requirements.txt` and `frontend/package.json`, with minimum versions past
  every known advisory. They are audited like ours (below) and updated by Dependabot.
- **Choosing a new one** (an extra, a template package or a CI tool): it must be actively maintained,
  under a license compatible with MIT, free of known vulnerabilities, and worth its weight; a new runtime
  dependency is normally refused. The decision is recorded in the pull request that adds it.
- **Obtaining:** CI tools are installed from PyPI with `pip install --require-hashes` from the locked
  files `ci/requirements-*.txt`, generated by `uv pip compile --universal --generate-hashes` from the
  `.in` files for the lowest Python version of the jobs that use them. GitHub Actions are pinned to full
  commit SHAs. The fuzzing image is pinned by digest.
- **Tracking:** Dependabot proposes updates weekly for Actions, the CI locks and the generated app's
  templates; each update goes through the same pull-request checks as any change.

## Software composition analysis (SCA)

- `vulnerability-audit.yml` runs `pip-audit` against every locked CI tool set (and every version pinned
  in them, including versions pinned only for another Python version) and the generated app's back end,
  and `npm audit` against its front end, on every change to them and weekly. On pull requests, GitHub's
  dependency review blocks any change that adds a dependency with a known vulnerability of **moderate**
  severity or higher.
- **Threshold:** a known vulnerability of medium or higher severity that affects sp2react or the apps it
  generates must be fixed before the next release, and within 60 days at the latest (30 days for high or
  critical). Low-severity findings are fixed in the next regular update. A finding that does not affect
  sp2react is recorded in `vex.openvex.json` with the reason.
- **No release with open violations:** the release checklist ({doc}`releasing`) requires a clean audit.

## Static analysis (SAST)

- CodeQL (security queries, Python and TypeScript) runs on every push and pull request and weekly;
  `ruff` (including the Bandit-derived `S` rules) and `mypy --strict` run on every push and pull request.
- **Threshold:** every CodeQL alert of **medium** severity or higher must be fixed or dismissed with a
  written reason before merging; `ruff` and `mypy` must be clean (a justified `noqa` is allowed and
  reviewed). These checks are required to pass before a pull request can be merged into `main`.
